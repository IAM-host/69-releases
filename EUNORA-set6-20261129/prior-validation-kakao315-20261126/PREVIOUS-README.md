# EUNORA 카카오 3.15.0 통합 수정본 · 2026-11-26

카카오 드라이버 3.15.0 대응을 이전 통합 수정본에 합친 누적 묶음입니다. 이전 통합본 v3와 비교해 새로 바뀐 앱 소스는 **E02.kt·ModuleMain.kt 두 개**입니다. 이전의 미사용 코드 정리와 로지 D1 21.55 수정·네이티브 연결도 포함하므로, 앞선 정리 ZIP이나 로지 ZIP을 먼저 적용할 필요가 없습니다.

콜마너 배지 표시와 대리·탁송 SET을 각각 3개로 나누는 SET 6개 UI 작업은 보류 상태이며 이 묶음에 포함하지 않았습니다. 기존 UI·GPS 설정 화면·L 프로그램은 이번 카카오 수정에서 바꾸지 않았습니다.

## 카카오 변경 내용

- 일반 목록은 즉시 반환과 비동기 완료를 모두 관찰합니다. 같은 캐시 객체도 조건 변경 후 다시 검사할 수 있습니다.
- 일반·프로·귀가지원 카드는 새 관리자에서 실제 게시되거나 대기열에 들어온 결과를 확인합니다. 카카오 자체 귀가지원 거절·자동 수락 상태는 유지합니다.
- 새 수락 이벤트·콜백·성공 결과 구조에 연결했습니다. 관리 중인 자동 요청의 콜백만 관찰하며, 수락한 콜 ID가 요청 ID와 일치해야 감지를 끕니다.
- 확인된 12개 업무 거절은 실패로 처리하고 감지는 유지합니다. 통신 오류·취소·알 수 없는 응답은 수락 여부를 확정하지 않습니다.
- 목록의 기사→출발지 거리 필드를 바로잡고, 예약 목록으로 잘못 등록했던 콜 재개 응답 훅을 제거했습니다.
- 새 APK에서 확인한 Java 진단·보고서 계약을 갱신했습니다. 제거된 RootingStatus 등록은 건너뛰며, 보고서의 미확인 항목·검사 오류·시간 정보는 보존합니다. 네이티브 검사 전체·Play Integrity·서버 판정 대응을 추가한 것은 아닙니다.

Debug·Release 컴파일과 Release 린트·R8·최종 APK 빌드를 통과했습니다. 실제 생산 코드에서 추출한 감지·매칭·수락 경로의 연결 검사 36개도 통과했습니다. 모든 검사는 실제 휴대폰이나 서버의 수락 성공을 대신하지 않습니다.

## 적용 방법

1. ZIP을 OneDrive 밖의 `C:\EUNORA-kakao315` 같은 새 폴더에 압축 해제합니다. Android Studio에서 편집 중인 파일을 먼저 저장하세요.
2. 압축을 푼 폴더에서 `Apply-EUNORA-All.cmd`를 실행합니다.
3. `app` 폴더와 `gradlew`가 함께 있는 **WheelProbe 프로젝트 폴더** 경로를 입력합니다.
4. 도구가 교체·삭제할 기존 파일을 프로젝트의 `EUNORA-all-backup-날짜시간` 폴더에 백업한 뒤, 파일을 적용하고 확인된 미사용 파일을 삭제합니다.
5. 본인 프로젝트에서 기존 서명 방식으로 APK를 빌드·설치합니다. 모듈 설정을 확인한 뒤 **카카오 드라이버를 강제 종료하고 다시 실행**합니다. 로지의 새 네이티브 등록이 반영되지 않으면 휴대폰을 재부팅해서 확인합니다.

CMD는 PC에서 프로젝트 파일을 적용하는 도구입니다. 적용 후 앱을 사용할 때마다 실행할 필요는 없습니다.

## 적용 대상과 포함 파일

카카오 수정은 제공된 **카카오 드라이버 3.15.0 / versionCode 3150099**의 아래 APK만 대상으로 합니다.

```text
cf38573177afbbb4ac0ed94165e225b6743c40087d70e76e440f30927df98b89
```

시작 시 APK SHA-256을 확인합니다. 버전 표시가 같아도 APK 바이트가 다른 빌드나 이후 업데이트에서는 카카오 연결을 설치하지 않습니다. 대상 APK가 달라졌다면 해당 APK를 다시 분석해야 합니다.

- **E02·ModuleMain:** 해당 카카오 APK에서 확인한 콜 감지·매칭·수락 경로와 초기 연결을 반영한 전체 파일입니다.
- **E03·E04·E06:** 이전 미사용 설치 함수·호환 클래스·연결되지 않은 구형 처리 코드 정리와 기존 앱 수정을 포함합니다.
- **E05·ProGuard 설정:** 이전 로지 D1 콜 감지·수락·Java 보고서 대응, 네이티브 연결과 JNI 이름 유지 설정을 그대로 포함합니다.
- **네이티브 추가 파일:** 등록 파일, 4개 ABI의 자체 `libeunora_logi_native.so`, C 소스·헤더, 선택적인 재빌드 스크립트입니다. 일반 APK 빌드에는 제공된 자체 부품을 사용하며, 해당 부품을 직접 재빌드할 때만 Android NDK가 필요합니다.
- **미사용 파일 4개 삭제:** `AutoClickService.kt`, `ExecutionClient.kt`, 사용하지 않는 접근성 XML, 잘못 중첩된 경로의 `ErrorReporter.kt`입니다. 정확한 경로는 `DELETIONS.txt`에 있습니다. 알려진 내용과 일치할 때만 백업 후 삭제합니다.

적용 목록은 총 15개 파일과 삭제 대상 4개입니다. 이번 카카오 수정에서 나머지 13개 적용 파일·기존 적용 도구·삭제 목록은 이전 v3와 동일합니다.

`E02.txt`~`E06.txt`와 `ModuleMain.txt`는 같은 전체 코드를 메모장에서 보기 위한 사본입니다. **TXT 여섯 개만 교체하면 네이티브 등록·추가 파일·미사용 파일 삭제가 반영되지 않습니다.** 적용 도구를 사용하거나 `update-manifest.json`의 전체 파일과 삭제 목록을 함께 반영하세요. TXT는 Android 소스 폴더에 추가하지 마세요.

## 적용 확인과 검증 범위

적용 도구는 검토된 원본·수정본의 정확한 SHA-256과 일치하는 파일만 바꿉니다. 다른 로컬 편집이 있으면 쓰기 전에 중단하므로, 현재 소스를 기준으로 병합해야 합니다. 이미 적용된 상태에서 다시 실행하면 파일을 바꾸거나 새 백업을 만들지 않습니다. 적용 중 오류가 발생하면 변경한 기존 파일과 삭제 파일을 백업에서 복원하고, 해당 실행이 만든 새 파일을 제거합니다.

적용 도구 검증은 Linux PowerShell 7.5.4에서 수행했습니다. 실제 Windows PowerShell 실행과 실제 Android 기기의 프레임워크 연결·콜 수신·수락·서버 동작은 아직 확인하지 않았습니다. 코드 검증이나 연결 로그만으로 실제 기기·서버의 성공을 보장하지 않습니다. 이전 v3 상태·원본 ZIP과 실제 첨부 파일 7개를 합친 상태·이미 적용된 상태를 검증했습니다. 적용 후 78개 기준 파일이 최종 프로젝트와 바이트 단위로 일치했고, 백업과 재실행도 확인했습니다. 새 로컬 편집 4개 사례는 파일을 쓰기 전에 중단했습니다. 세부 결과는 `APPLY-INTEGRATION.json`과 최종 검증 보고서를 확인하세요.

USB 연결 후 platform-tools CMD에서 다음 명령을 실행하고 카카오 드라이버를 켜면 카카오 연결 로그를 볼 수 있습니다.

```cmd
adb logcat -v time -s EUNORA_KAKAO
```


`profile verified versionCode=3150099`와 감지·수락 관찰자 `installed`는 해당 실행에서의 설치 상태를 보여 줍니다. `ACCEPT_CONFIRMED`는 관리 중인 요청과 일치하는 성공 응답을 관찰한 경우입니다. `ACCEPT_UNCONFIRMED`는 수락 여부를 확정하지 못해 중복 요청을 막고 대기하는 상태입니다. 이때 카카오의 실제 배차 상태를 먼저 확인해야 합니다. 대기 상태는 ON/OFF만으로 새 요청을 보내도록 풀리지 않습니다.

## 기존 로지 네이티브 적용 범위

기존 네이티브 처리는 제공된 **로지 D1 21.55 / versionCode 632의 메인 프로세스·APK·ARM64 라이브러리**가 일치할 때만 확인된 루팅 판단 함수에 적용합니다. D2·다른 버전·다른 ABI의 동작은 확인하지 않았습니다. 원래 SDK 초기화·암호화·인증과 해당 함수의 원래 실행은 유지합니다. 설치 앱 조회·EUNORA 숨김과 다른 모든 보안 검사 처리는 포함하지 않았습니다.

로지 연결 로그는 다음 명령으로 확인합니다.

```cmd
adb logcat -v time -s EUNORA_LOGI_NATIVE
```

`WAIT_TARGET`은 대상 라이브러리 로드를 기다리는 상태이며, `Verified native rooting leaf hook active`는 확인한 함수에 연결됐다는 뜻입니다. `Verified native rooting result normalized`는 원래 판정이 true였던 호출을 처리했다는 뜻입니다. 원래 false인 호출에서는 마지막 메시지가 없어도 됩니다. 이 로그는 서버의 허용 여부를 증명하지 않습니다.
