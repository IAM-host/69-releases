# L — EUNORA 자동 점검과 REA 분석

기존 L의 6개 탭과 화면 스타일을 유지하면서 EUNORA 자동 점검, REA 분석, 7개 앱 프로필, 관찰용 훅 생성, 보안 테스트 훅 생성과 생성본 빌드 검사를 추가했습니다. AI 모델 연결은 이번 범위에서 제외했습니다.

**`main.py`만 교체하지 마세요. ZIP 전체를 새 폴더에 풀어 사용해야 합니다.** 기존 L의 사용자 데이터는 ZIP에 포함하지 않습니다.

## 기존 전달본에서 업데이트

이미 REA 설치를 마쳤다면 L을 닫고, 새 ZIP 안 `L` 폴더의 파일을 기존 `L` 폴더에 덮어쓴 뒤 `run_L.bat`를 실행하세요. ZIP에는 `.venv`, REA 설정·설치 도구, 사용자 분석 데이터가 포함되지 않아 기존 폴더의 설치를 이어서 사용할 수 있습니다. EXE로 사용 중이라면 소스 업데이트 후 `build_L.bat`로 다시 빌드해야 합니다.

## Windows에서 실행

1. Python 3.10 이상을 설치하고 `run_L.bat`를 실행합니다. 첫 실행은 인터넷으로 이 폴더의 `.venv`에 PySide6를 설치합니다.
2. REA 기능에는 지원되는 Node.js와 **전체 JDK 17 이상**이 필요합니다. Node.js 24 LTS와 JDK 21을 권장합니다. Android Studio의 `jbr`도 `jdk.compiler`를 포함하면 사용할 수 있습니다.
3. `setup_rea.bat`를 실행합니다. REA 6.8.0을 이 폴더의 `tools/rea`에 설치하고, 전용 `jadx-headless-mcp 0.7.1` JAR를 내려받아 SHA-256을 확인합니다. Node/JDK 자체는 자동 설치하지 않습니다. 설치에는 인터넷이 필요합니다.
4. 프로그램의 **구조 분석 → REA 설정**에서 경로와 사전 검사를 확인합니다. 기본 분석 제한 시간은 300초이며 큰 APK는 설정에서 늘릴 수 있습니다.

지원되는 Node 버전은 22.23.4 이상인 22.x, 24.22.1 이상인 24.x, 또는 26.12.1 이상입니다. 일반 JADX 설치와 REA의 전용 headless JAR는 서로 다릅니다. 기존 JADX XREF 기능은 별도 JADX 경로를 계속 사용합니다.

자동으로 경로를 찾지 못하면 다음처럼 지정할 수 있습니다.

```cmd
.venv\Scripts\python.exe install_rea.py --node "C:\Program Files\nodejs\node.exe" --java-home "C:\Program Files\Android\Android Studio\jbr"
```

USB 추출·로그 기능에는 Android SDK platform-tools의 `adb.exe`가 필요합니다. 직접 Python으로 실행할 때는 `python -m pip install -r requirements.txt` 이후 `python main.py`를 실행합니다.

## EUNORA 자동 점검 — 기본 작업 흐름

일반적인 EUNORA 점검에서는 클래스 이름을 직접 입력할 필요가 없습니다.

1. **구조 분석 → EUNORA 자동 점검**에서 APK와 EUNORA 프로젝트 폴더를 선택합니다. 프로젝트 안의 `ModuleMain.kt`를 지정해도 됩니다.
2. APK 패키지로 7개 앱 중 대상을 구분하고, 해당 E파일과 ModuleMain을 확인합니다. 선택 E파일의 직접 명시된 클래스와 연결 가능한 메서드 이름을 수집합니다.
3. REA가 APK 클래스 목록을 읽고 기존 코드의 대상을 대조합니다. 확인한 클래스의 상세 정보도 최대 24개까지 자동 조회합니다. 나머지는 정밀 조회를 미룬 대상으로 표시합니다.
4. 결과는 발견·APK에서 미발견·추가 확인·조회 오류·정밀 조회 대기로 구분합니다. 동적으로 계산된 이름, 상속, 스코프를 확정하지 못한 표현은 별도로 표시합니다.
5. **점검 결과로 훅 생성**에서 확인된 메서드를 선택하면, 클래스 이름을 다시 입력하지 않고 기존 생성기로 연결합니다. 이후 **생성본 빌드 검사**를 사용할 수 있습니다.

점검은 선택 E파일의 정적으로 해석 가능한 클래스·메서드 이름을 대상으로 합니다. ModuleMain은 함께 해시를 기록하지만 전체 Kotlin 동작을 해석하지 않습니다. 이름을 찾았다는 결과는 정확한 인자형이나 실제 훅 실행을 증명하지 않습니다. 미발견 역시 상속·split APK·런타임 로딩 등의 가능성이 있어 수정이 확정됐다는 뜻은 아닙니다.

APK나 원본 코드가 점검 후 변경되면 그 점검 결과로 생성하지 않습니다. 새 점검을 실행하세요. 보고서는 `eunora_audits`에 저장하며, 원본 Android 파일은 변경하지 않습니다.

수동 **REA 분석** 메뉴는 보고서에서 더 살펴볼 부분을 정밀하게 분석할 때 사용합니다.

## REA 분석 사용

1. **구조 분석** 탭에서 APK를 선택합니다.
2. **REA 분석**을 누르고 APK 정보, 클래스 검색, 클래스 정보, 메서드 분석, 참조 분석 중 하나를 선택합니다.
3. 클래스·메서드·오버로드 등 필요한 대상을 입력해 실행합니다. 결과는 기존 분석 결과창에 표시하고 전체 JSON은 `rea_results`에 저장합니다.

실제 REA CLI를 실행합니다. 실패를 기존 분석 성공 결과로 바꾸지 않으며, 오류와 부분 결과를 구분합니다. 분석은 작업 스레드에서 실행하고 창을 닫으면 진행 중인 작업에 취소를 요청합니다.

## AI 없는 EUNORA 관찰용 코드 생성

관찰용 모드의 생성 범위는 **선택한 정확한 메서드의 실행을 기록하는 훅**입니다. 보안 테스트 모드는 아래 별도 절차에서 선택합니다. 임의의 새 기능이나 콜 수락 로직을 추론하는 생성기는 아닙니다. 인자·반환값·예외를 변경하지 않고 호출 여부, 인자 개수, 결과 타입 등을 로그로 남깁니다.

1. REA로 대상의 **클래스 정보**를 분석합니다. 검색 결과나 메서드 본문만으로 생성하지 않습니다.
2. **훅 지도 → 훅 코드 생성**에서 앱 프로필, 기존 EUNORA 프로젝트 또는 그 안의 `ModuleMain.kt`, 정확한 메서드·오버로드를 선택합니다. APK는 구조 분석에서 선택한 파일입니다.
3. 생성 시 APK 패키지와 SHA-256을 대조하고 DEX의 실제 선언 클래스·원형·접근 플래그를 확인합니다. 클래스 별칭은 실제 DEX 대상이 하나일 때만 해석합니다.
4. `generated_hooks`에 **전체 ModuleMain.kt와 해당 E파일 사본**, 같은 내용의 TXT, `changes.diff`, `manifest.json`을 만듭니다. 원본 프로젝트를 덮어쓰지 않습니다. 같은 대상의 기존 생성 블록은 중복 추가하지 않고 갱신합니다.
5. **생성본 빌드 검사**를 누르면 프로젝트를 별도 폴더에 복사하고 생성본만 적용하여 `:app:compileDebugKotlin`을 실행합니다. 결과와 로그 경로를 표시합니다. 원본·생성본이 생성 후 바뀌면 검사를 중단하고 다시 생성을 요구합니다.

프로필은 카카오(E02), T맵(E03), 콜마너1·2(E04), 로지D1·D2(E05), 아이드라이브(E06)입니다. 기존 `onPackageLoaded`와 설치 함수 위치를 확인할 수 있는 프로젝트만 지원합니다. 자동으로 불명확한 위치에 삽입하지 않습니다. 생성 폴더는 Android 원본 프로젝트 밖에 있어야 합니다.

빌드에는 프로젝트의 Gradle wrapper JAR, 해당 프로젝트에 맞는 JDK·Android SDK·의존성·로컬 설정이 필요합니다. 일반 Debug 변형을 기준으로 Kotlin 컴파일을 검사합니다. 다른 flavor를 사용하는 프로젝트는 생성 사본에서 해당 변형을 별도로 빌드하세요. 빌드 성공과 기기에서의 훅 실행 확인은 별도입니다. 실제 기기에서 새 APK 설치·LSPosed 적용·프로세스 재시작 후 `L_OBSERVER` 로그를 확인해야 합니다.

## 보안 자동 점검과 테스트 훅 생성

공동 개발 앱의 보안 검사 동작을 확인하는 별도 흐름입니다. 기존 EUNORA 코드를 입력으로 읽고 수정 사본을 생성합니다.

1. **구조 분석 → 보안 자동 점검**에서 APK와 EUNORA 프로젝트를 선택합니다.
2. DEX 명령의 실제 문자열·호출 위치를 읽어 root 파일, su 명령, 루트 관리자 패키지, 후킹 프레임워크·스택·메모리 검사 관련 후보를 찾습니다. 일반 화면 이름의 `RootActivity` 같은 단어만으로 판정하지 않습니다.
3. REA와 실제 DEX 선언으로 후보의 클래스·메서드·원형을 대조합니다. 한 번에 최대 12개 클래스를 상세 조회하며, 테스트 코드를 만들 수 있는 후보부터 확인합니다. 오류·보류·미지원·후보 반환 한도는 결과에 표시합니다.
4. **보안 테스트 훅 생성**을 눌러 확인된 후보와 동작을 선택합니다. 클래스 이름을 직접 입력할 필요가 없습니다.

| 동작 | 생성 코드의 역할 |
|---|---|
| 호출 관찰 | 원래 호출의 인자·결과·예외를 유지하고 실행 정보를 기록합니다. |
| 테스트: Boolean 결과 false | 원래 메서드를 실행한 뒤, 예외가 없는 primitive Boolean 결과를 false로 변경합니다. |
| 테스트: void 검사 실행 생략 | 선택한 void 메서드 본문을 실행하지 않습니다. 그 본문의 부수 효과와 예외도 발생하지 않습니다. |

결과 변경·실행 생략 코드는 **대상 앱 패키지와 EUNORA 모듈의 패키지를 설치 시점과 콜백에서 확인**합니다. Debug/Release에 따른 실행 제한은 없습니다. 기존 Gradle의 BuildConfig 설정을 바꾸지 않으며, 같은 생성 코드를 두 빌드 종류에 사용할 수 있습니다. 실제 설치·호출은 기기에서 확인해야 합니다.

후보에 지원되는 모드만 선택할 수 있으며, 지원하지 않는 모드로 대상이 바뀌면 동작을 다시 선택해야 합니다. 결과 변경용 생성은 현재 APK를 다시 탐색해 같은 후보·원형·접근 플래그가 확인될 때만 진행합니다. 전체 E파일·ModuleMain·TXT·diff·manifest를 새 폴더에 만들고 기존 **생성본 빌드 검사**로 이어집니다.

후보 탐색은 메서드의 전체 업무 의미나 실제 실행을 증명하지 않습니다. 선택한 메서드가 테스트 목적에 맞는지 변경 내역으로 확인하세요. 네이티브·리플렉션·동적 문자열·분리 APK·서버 판정은 이 탐색만으로 전부 확인할 수 없습니다. 무결성 증명·서명·서버 토큰 관련 후보는 결과 변경 대상에서 제외합니다. DTO·생성자·기타 반환형도 현재 결과 변경 템플릿의 지원 범위가 아닙니다.

이전 버전에서 생성한 코드에는 Debug 제한이 남아 있을 수 있습니다. 새 버전에서 해당 대상을 다시 생성하면 같은 ID의 생성 블록을 갱신합니다. 생성 메타데이터의 `debug_only: false`, `debug_guard: null`은 빌드 종류 제한이 없다는 뜻입니다.

보안 보고서는 `security_audits`에 저장합니다. 공개 배포 ZIP에는 사용자 APK·분석 원문·설치된 외부 도구를 포함하지 않습니다. 기기에서 확인할 로그 접두사는 `L_SECURITY_TEST`입니다.

## Windows의 한글 경로와 빌드 검사

Windows에서는 빌드용 프로젝트 사본을 짧은 ASCII 경로에 만듭니다. 기본 위치는 `%LOCALAPPDATA%\L-build`이며, 한글 사용자 경로나 쓰기 권한 등으로 사용할 수 없으면 `%PUBLIC%` 또는 임시 폴더의 영문 경로를 확인합니다. L 프로그램과 생성본 폴더를 바탕 화면에서 옮길 필요는 없습니다.

직접 위치를 지정하려면 `L_BUILD_DIR` 환경변수에 짧고 쓰기 가능한 영문 절대 경로를 지정할 수 있습니다. 원본 Android 프로젝트 밖의 폴더여야 합니다. 검사에 사용한 실제 프로젝트 경로는 결과창에 표시합니다.

`build.log`와 검사 결과 JSON은 기존 생성본의 `build_checks` 안에 보관합니다. 실패 시 Gradle의 `What went wrong` 및 Kotlin 오류 발췌를 화면에 바로 표시하고, 헤더와 JSON의 빌드 상태도 함께 갱신합니다. 원본 프로젝트의 Gradle 경로 검사 설정은 바꾸지 않습니다.

## L.exe 만들기와 데이터 위치

Windows에서 `build_L.bat`를 실행하면 PyInstaller가 `dist\L.exe`를 만들고 **이 소스 폴더의 `L.exe`로 복사**합니다. `setup_rea.bat`를 실행한 같은 폴더의 `L.exe`를 사용하세요. 현재 전달물은 소스이며 Windows에서 빌드한 EXE를 포함하지 않습니다.

프로그램은 실행 파일 옆의 `rea_settings.json`, `tools`, `sessions`, `apks`, `hooks.json`, `eunora_hooks.json`을 사용합니다. 다른 폴더로 이동할 때에는 필요한 설정·도구·데이터도 함께 이동하고 **REA 설정에서 절대 경로를 다시 확인**하세요. 소스로 실행하면 `main.py` 옆을 사용합니다. `L_APP_DATA_DIR`로 별도 데이터 폴더를 지정할 수도 있습니다.

분석 원문, 생성 코드, 로그는 사용자 데이터입니다. APK 분석 원문에는 앱 내 문자열·설정이 포함될 수 있으므로 공개 저장소에 그대로 올리지 마세요. 배포 ZIP에는 이 데이터나 설치된 외부 도구를 넣지 않습니다.

## 내부 구조와 유지된 기능

- `main.py`: 실행 진입점, `l_app/ui.py`, `rea_dialogs.py`: 기존 화면과 추가 기능 대화상자
- `eunora_audit.py`, `source_catalog.py`: 앱 자동 식별·기존 E파일 대상 수집·자동 대조
- `rea.py`: REA 실행·환경 검사·근거 저장, `install_rea.py`: 고정 버전 로컬 설치
- `generator.py`, `eunora_profiles.json`: 검증된 대상의 관찰용 Kotlin 사본 생성
- `security_scan.py`, `security_audit.py`: 보안 단서 탐색과 실제 대상·원형 대조
- `security_generator.py`, `security_dialogs.py`: 명시적으로 선택한 보안 테스트 코드 생성과 UI
- `build_validation.py`: 원본 해시 확인과 격리된 Android 빌드 검사
- `analysis.py`, `adb.py`: 기존 APK/DEX/JADX 분석·USB 기능
- `jobs.py`, `processes.py`: 작업 스레드와 취소 가능한 외부 명령
- `logs.py`, `state.py`, `paths.py`, `workflows.py`, `config.py`: 로그·저장·대조·원본 보존·앱 정보

기존 로그·세션·후보군·추출/비교·구조 분석·훅 지도 기능을 유지했습니다. 한글 로그 청크 복원, 실패 시 원본 보존, 정확한 Kotlin 문자열 치환, 오래된 분석 결과의 복사본 생성 중단도 유지합니다. 정적 문자열 발견은 실행된 훅의 증거로 표시하지 않습니다.

## 검증

`run_tests.bat` 또는 `python -m pytest -q`로 검사합니다. GUI 검사는 Qt offscreen 모드입니다. 검사 환경·결과와 전달 파일 해시는 `VALIDATION.json`에 기록합니다.

실제 APK로 REA 정보·클래스·검색·메서드·참조 분석을 실행하고, 확인된 메서드의 관찰용 훅 사본을 생성하여 Android Kotlin 컴파일을 검사했습니다. 합성 APK/프로세스·실제 Qt 작업 스레드로 오류·취소·파일 보존·UI 연결도 검사합니다. Windows EXE 실행과 실제 휴대폰에서의 훅 실행은 별도 확인이 필요합니다.

완성형의 역할과 현재 구현 범위는 `DIRECTION.md`에 정리했습니다.

기존 EUNORA 보안 코드에서 실제 값 변경과 로그 전용 처리를 구분한 내용은 `EXISTING_SECURITY_REVIEW.md`에 정리했습니다.
