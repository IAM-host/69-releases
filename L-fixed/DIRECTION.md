# L의 개발 방향

L은 EUNORA를 개발하고 유지보수하는 PC용 작업 도구를 목표로 합니다. 휴대폰에서 EUNORA가 콜을 감지하고 처리하는 동안, L은 APK와 기존 프로젝트를 분석하고 수정 사본과 검증 결과를 정리합니다.

## 완성형의 작업 흐름

1. 사용자가 대상 APK와 EUNORA 프로젝트를 선택합니다. 앱별로 클래스 이름부터 입력하는 과정은 기본 흐름에서 줄입니다.
2. 패키지로 카카오·T맵·콜마너1/2·로지D1/D2·아이드라이브를 구분하고 해당 E파일과 공통 코드의 관계를 찾습니다.
3. 기존 코드의 대상 클래스·메서드·데이터 구조를 APK와 대조합니다. 콜 데이터 감지, 조건 판정, 수락 요청, 성공 응답을 각각 구분해서 점검하는 방향입니다.
4. 업데이트 전후 자료와 기존 규칙으로 변경 후보를 찾고 근거를 표시합니다. 대상이 하나로 확정되고 수정 규칙이 있는 범위에서 코드 사본을 생성합니다. 구조가 달라졌거나 여러 후보가 있는 부분은 추가 분석 대상으로 남깁니다.
5. 전체 E파일과 ModuleMain 사본, TXT, diff를 제공하고 원본을 보존합니다. 사본에서 빌드를 검사하고 오류를 결과에 연결합니다.
6. 기기 로그에서 실제 감지·조건 판정·요청·응답이 어디까지 진행됐는지 보여주는 흐름을 목표로 합니다. 클래스 발견·컴파일 통과·기기 동작 확인은 서로 다른 상태로 관리합니다.
7. 사용한 APK와 소스의 해시, 분석 결과와 변경 내용을 버전별로 묶어 다음 업데이트 때 재사용하는 방향입니다.

예를 들어 카카오 업데이트 후 콜 감지 위치가 달라졌다면, 기존 E02와 APK를 비교해 어떤 기존 대상이 발견되는지 먼저 확인합니다. 미발견 대상은 이전 APK와 구조를 비교해 새 후보를 좁히고, 확인한 수정 사본을 빌드한 뒤 기기 로그로 확인하는 것이 목표 흐름입니다.

## AI 없이 자동화하는 원리

이미 알려진 패키지·파일 배치·반복되는 훅 형식은 규칙과 템플릿으로 처리할 수 있습니다. APK 메타데이터와 소스에 정확히 적힌 대상을 찾아 대조하고, 검증된 메서드 원형을 정해진 Kotlin 형식에 넣는 작업에는 AI가 필수는 아닙니다.

새로운 앱 구조의 의미를 해석하거나 변경 후보를 추론하는 범위는 별도의 분석과 구현이 필요합니다. 향후 AI를 연결하면 그런 분석과 수정 제안에 사용할 수 있습니다. AI의 제안도 APK 근거·원본 보존·빌드·기기 확인 절차를 거쳐야 합니다.

## 이번 버전의 실제 범위

- REA APK 개요·클래스·메서드·참조 분석을 실행합니다.
- EUNORA 자동 점검은 APK 패키지로 앱을 구분하고, 선택 E파일의 정적으로 해석 가능한 클래스와 메서드 이름을 자동 대조합니다. ModuleMain도 입력 해시로 함께 묶습니다.
- 확인한 메서드를 목록에서 선택하여 기존 생성기로 넘길 수 있습니다. 클래스 이름을 다시 입력할 필요가 없습니다.
- 관찰용 템플릿은 인자·결과·예외를 유지하고 호출 정보를 기록합니다.
- 별도의 보안 자동 점검은 DEX 지표로 후보를 찾고 실제 원형을 대조합니다. 확인한 후보에는 디버그 EUNORA에서만 활성화되는 Boolean 결과 false 또는 void 본문 실행 생략 테스트 코드를 생성할 수 있습니다. 모드·지원 범위는 명시적으로 구분합니다.
- 수정 사본의 Debug Kotlin 컴파일과 원본 보존을 검사합니다.

조건 판정 전체의 의미 해석, 업데이트 전후 구조 매칭, 새로운 수락 로직 작성, 기기 로그의 단계별 자동 진단은 추가 개발 영역입니다. 따라서 이번 버전의 자동 점검 보고서는 EUNORA 전체 동작이 정상이라는 보증이 아니라, 현재 입력으로 정적으로 확인한 범위와 미확인 범위를 보여줍니다.
